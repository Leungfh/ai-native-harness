# 一次发布说明生成器的迭代

包内的 `example/release_note.py` 可以运行。下文中的 DOCS-PORTAL、Issue、PR、CI 编号、部署和观测结果均为教学设定。实际接入时只把本项目的记录和证据填入 Excel。

## 第一次接入时，发给 Codex

在待接入的仓库中打开 Codex，将下面这段作为第一次任务。

> 读取适用于当前目录的 AGENTS.md、README、依赖清单、锁文件、测试和现有工作流。引用文件路径说明应用入口、现有验证命令、构建产物和发布方式。把已证实的事实补入 docs/harness/PROJECT.md，把待负责人补充的事项标为“待确认”。比较模板与现有文件，合并已有规则并保留本地改动。用项目的实际命令配置 harness.config.json，运行 python3 scripts/harness.py doctor 与 python3 scripts/harness.py check。在独立分支整理改动，给出执行命令、退出结果、待补证据和首个可独立验收的业务任务。本次交付范围为工程接入和本地验证。

## 从想法到可复现的验收

| 时点 | 人员与决定 | 记录去向 |
| --- | --- | --- |
| 收集 | 文档编辑演示：手工写发布说明时，版本标题不一致，空条目有时会出现在网页上。提出 IDEA-001。 | 在“想法池”登记 DOCS-PORTAL / IDEA-001，在 `docs/harness/IDEAS.md` 或 Issue #12 记录问题样本。 |
| 取舍 | 产品负责人将“一个版本标题、一份非空的有序变更清单”纳入 v0.2.0。自动翻译单独保留，等确认语言需求后再评估。 | 想法状态选“采纳”，关联 Issue #12、目标版本和规格。 |
| 实现 | 维护者选择项目现有 Python 测试入口。Codex 实现渲染函数并关联 PR #18，审查人根据下列输入核对行为。 | 从 `docs/harness/SPEC.md` 建立 `docs/harness/specs/issue-12.md`，写入验收条件，在“实施清单”关联 Issue 和 PR。 |

| 验收条件 | 可直接尝试的输入 | 应观察到的结果 |
| --- | --- | --- |
| AC-1 标题和项目符号 | `render_release_note("v0.2.0", ["新增导出", "修正标题"])` | 输出下方 Markdown 原文，条目顺序与输入一致，末行以换行符结尾。 |
| AC-2 清理空白 | `render_release_note(" v0.2.0 ", [" ", " 修正标题 "])` | 标题为 `# v0.2.0`，只有一条 `- 修正标题`。 |
| AC-3 拒绝无有效内容 | 分别尝试 `render_release_note("v0.2.0", [" "])` 与 `render_release_note(" ", ["修正标题"])`。 | 两次都抛出 `ValueError`。若函数返回空标题、空条目或仅有标题的页面，就应退回修订。 |

```markdown
# v0.2.0

- 新增导出
- 修正标题
```

要检验这一段，在包内 `example/` 目录运行 `python3 -m unittest -v test_release_note`。4 项测试应全部通过。要同时观察未配置时的退出码、真实构建产物和主动引入回归后的失败输出，可按独立副本的步骤操作。[本地演练与 Windows 命令](../example/README.md)

接入实际仓库后，PR 记录还要标出测试运行对应的提交和候选产物。假设在 DOCS-PORTAL 的 PR #18，审查人发现初稿会保留空条目，便贴上 AC-2 的失败输出。开发者修正后，审查人以同一输入复测，把 CI #81 和候选产物 `docs-81` 关联到 PR。

## 从预发布到回滚

DOCS-PORTAL 的真实交付物在本例中设定为一组文档页面。其一个历史栏目通过标题自动生成导航。候选产物先在预发布站通过正文检查，上线负责人安排一个栏目试发。同时用 `docs/harness/RELEASE.md` 建立 v0.2.0 独立发布记录，在关联 Release Issue 中登记本次候选提交、产物与观察条件：自发布起 10 分钟内，两个已有导航入口只要有一个无法跳到本期说明，就停止推广，并切回上一产物 `docs-76`。团队已演练旧产物恢复；这次变更无需迁移数据。

| 节点 | 证据（模拟） | 填表与行动 |
| --- | --- | --- |
| 放行试发 | `docs-81` 的 CI #81、预发布正文对照、旧产物恢复演练以及值班人员均已确认。 | 在“发布门禁”逐项录入责任人与证据；G06 记录“不适用”、负责人和理由“仅生成 Markdown，无存储变更”。G07 按本次依赖与权限差异判断。 |
| 第 4 分钟 | 入口 A 与 B 均能打开页面；B 使用旧锚点，跳到了页面顶部。命中预设回滚条件。 | 发布负责人停止其他栏目推广，将试发栏目恢复到 `docs-76`，关联部署记录 #27、恢复记录 #28。 |
| 第 8 分钟 | 恢复后重复打开 A、B 两个入口，均准确跳到上一期对应正文，恢复检查截图附在记录 #28。 | 在“版本记录”选择“已回滚”。`docs/harness/CHANGELOG.md` 写明候选 v0.2.0 灰度回滚，当前对外服务的是 v0.1.0。 |

这次单元测试只覆盖了生成的文本。旧栏目的导航依赖另一套模板生成出来的锚点，预发布检查遗漏了从历史链接进入的路径。因此，“版本驾驶舱”里的放行准备状态和“版本记录”里的实际结果分别保留。

## 将复盘变成下一版验收项

Issue #23 记录旧入口 B、上一版目标锚点，以及候选页面实际生成的锚点；负责人将修复排入待验证版本 v0.2.1。新的验收条件是：在预览站访问两条历史链接，浏览器定位到指定发布说明的可见标题。把 Issue #23 加入“想法池”或关联现有想法，将这个入口检查写入下一版规格。待新版本实际发布后，再填入新的结果。

第二个使用其他语言构建的文档站也可以复用 AC-1 至 AC-3 的输入输出与“旧链接定位正确”这条整站验收。其负责人只需在自己的 `harness.config.json` 绑定本项目的测试和构建命令，按所在平台填写发布观察与恢复方式。
