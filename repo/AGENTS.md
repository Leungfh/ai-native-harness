# Codex 项目协作约定

本仓库采用 AI Native Harness，通过项目指令、可复用能力与项目数据，让 Codex 在约定范围内协助开发、验证和迭代。适用范围是本文件所在目录及其子目录。接入已有仓库时，请把所需条款合并进已有约定，保留项目原有的规则与事实。

## 开始一项任务

1. 先读 `docs/harness/PROJECT.md`、任务所在目录的指令、对应 Issue 及已有规范。用包清单、锁文件、原有 CI 和实际源码核对分支、运行时、命令与模块路径。将仍未知的事实和阻碍写进任务。
2. 说明本轮要改变的用户行为、成功条件和改动边界。小改动可把可验证条件直接写在 Issue 或 PR；跨模块、兼容性、数据或发布行为变化时，使用 `docs/harness/SPEC.md` 建立独立规格。新想法登记到 `docs/harness/IDEAS.md` 所述入口，排期后再进入实施。
3. 在任务分支中沿用现有目录、命名、格式化、异常处理和测试约定。先查已有实现与调用方，再做最小改动；新增或修复核心行为时补能判定结果的测试。保留工作区中与本任务无关的改动。
4. 从仓库根目录执行 `python3 scripts/harness.py doctor` 验证接入结构，再执行 `python3 scripts/harness.py check` 运行项目检查。记录命令、退出结果和对应提交。将检查失败或无法运行的原因、受影响的验收项和下一步写进 PR。日常运行时、依赖与命令见项目卡。
5. 提交遵循目标仓库惯例。尚无约定时使用 `feat:`、`fix:`、`docs:` 或 `chore:` 等前缀。按 PR 模板连接 Issue、验收条件与证据。核心逻辑、数据迁移、权限或发布路径变更须指出受影响模块，并交由相应维护者复核。
6. 上线由项目卡指定的发布责任人依据真实流程作出决定，记录在版本发布单。生产凭据通过平台的受控环境注入，仓库只保存配置名或示例值；日志与示例数据先脱敏。复盘中发现的需求用新 Issue 承接。

## 项目入口

| 需要回答的问题 | 入口 |
| --- | --- |
| 服务对象、技术栈、架构、目录和真实命令是什么？ | `docs/harness/PROJECT.md` |
| 本次改动怎样验收？ | 对应 Issue 或 `docs/harness/SPEC.md` 的任务副本 |
| 已采纳功能如何从规格推进到可评审 PR？ | `.agents/skills/feature-delivery/SKILL.md` |
| 是否具备上线条件、异常时怎样恢复？ | `docs/harness/RELEASE.md` 的版本副本 |
| 新想法进哪一版、已上线版本改变了什么？ | `docs/harness/IDEAS.md`、`docs/harness/CHANGELOG.md` |
| 何时采用 Hooks、子代理、外部工具或无人值守流程？ | `docs/harness/EXTENSIONS.md` |

## Code Review Rules

- 按变更位置核对适用规则。跨模块修改列出各自入口、局部规则差异和共享接口的调用方。对生成文件应找到生成命令并按仓库约定一同验证源码与产物。
- 保留能复现回归的断言。变更公共接口、数据或权限时，用旧输入、失败路径和实际调用方检验兼容性。每项审查意见附位置、依据、影响和复测方式。
- 首次接入从 Initial.md 开始。验证、审查和发布交接分别读取对应的 code-verification、pr-review-rules、release-readiness 技能。长任务按 docs/harness/PHASE.md 交接，影响多模块的架构选择按 docs/harness/ADR.md 归档。
