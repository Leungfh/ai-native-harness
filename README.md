# AI Native Harness｜用 Codex 接入 GitHub 项目并持续发版

**工程指南与配套模板 v1.1.0 · 2026-11-24**

第一次接入的成果是一份可评审的 PR。接手的工程师应能通过它找到项目入口，在干净环境运行真实测试，确认本次变更怎样验收，并知道发布出错时谁来恢复。做到这一步，再根据项目遇到的问题逐项增加自动化。

## 1 · 从一个现有项目开始

| 顺序 | 谁做什么 | 做完后留下什么 |
| --- | --- | --- |
| 选择试点 | 项目负责人选定一个 GitHub 仓库、一个目标版本和一个规模可控的真实 Issue。新仓库先确定最小用户行为和第一个可运行入口。 | 项目代号、版本、Issue、验收人。文件包版本 v1.1.0 与该项目的业务版本分别维护。 |
| 盘点差异 | 在解压目录运行 `python3 tools/kit.py plan "/目标仓库路径"`。让 Codex 在工作分支核对 README、项目指令、依赖清单、锁文件、测试、工作流和现有发布方式。 | 每个同名文件的处理决定；已证实的命令、产物和负责人写入项目卡。 |
| 接入文件 | 将 `repo/` 下适用的内容合并到目标仓库根目录，包含以点开头的目录。已有 AGENTS.md、PR 模板、CI 或发布规范按条合并；规则和历史证据只维护一处。 | 一个接入 PR，含项目卡、工作指令、校验配置及必要的仓库模板。 |
| 验证接入 | 在目标仓库根目录执行下列两个命令。先接入真实测试、lint 和构建，再在试验分支制造一处可恢复的回归，观察 CI 失败与修复后的结果。 | 失败和成功运行各自对应的提交；成功构建生成的产物、位置或标识。 |
| 交付第一版 | 用一个真实需求走完规格、实现、PR、预演、发布决定和观察。把 Issue、PR、提交、产物和发布记录关联回工作簿。 | 一条从需求到用户可见结果的记录；未达到条件的事项有负责人和下一动作。 |

在已接入的业务仓库根目录运行（Python 3.9+，Windows 可用 `py -3`）：

```sh
python3 scripts/harness.py doctor
python3 scripts/harness.py check
```

`doctor` 只检查关键文件及配置格式。原始模板的 `check` 会因未接入业务命令而返回 2；把该仓库真正使用的命令填入 `harness.config.json` 后再运行。测试必须有能判定业务结果的断言。没有单独 lint 或构建环节的项目，分别填写具体的 `skip_reason`。仓库已有 CI 时，可在原作业里调用检查入口，避免同一测试重复跑两次。

**启动 Codex**：在目标仓库打开会话，提供 [Initial.md](repo/Initial.md) 和解压后的文件包路径，再发出文件开头的任务。已使用 v1.0.0 的项目可从 [迁移步骤](MAINTENANCE.md) 开始。

## 2 · 四层架构如何落在仓库里

| 附件中的层 | 应解决的问题 | 默认入口及检查方法 |
| --- | --- | --- |
| 记忆层 | 换一个会话或维护者，能否找到项目事实？ | 根目录 `AGENTS.md` 放协作约定，`docs/harness/PROJECT.md` 指向真实架构、配置、依赖和命令。请新会话指出关键流程对应的文件，再与源码核对。 |
| 扩展层 | 一项反复出现的工作能否可靠复用？ | `.agents/skills/feature-delivery/SKILL.md` 定义从需求到可审 PR 的操作。需要并行调查、工具事件或提交前反馈时，按 `EXTENSIONS.md` 为对应客户端注册子智能体或钩子并验证触发。 |
| 集成层 | 外部工具、CI 和目标环境分别允许哪些动作？ | `.github/workflows/harness-ci.yml` 运行真实业务检查。部署接入现有平台。MCP 优先试用一个只读场景，用已知 Issue 比对回答，并记录权限范围、预算和退出办法。 |
| 编程层 | 改动能否按用户可观察到的行为验收？ | `docs/harness/SPEC.md` 记录输入、预期输出、反例与兼容性。沿用目标项目已有源码、测试和构建结构，PR 逐项关联证据。 |

现有 `.ai/` 资料可以由项目指令引用。Codex 项目说明以实际工作目录加载的 `AGENTS.md` 为准，其他客户端、Git hooks 与 MCP 各有配置入口。PR 上必须执行的检查要在服务端 CI 复验。工具路径和启用、试跑、停用的方法见包内 `repo/docs/harness/EXTENSIONS.md`。

### 如何沿用仓库已有的工程约定

- **目录与文件归属**。项目卡注明源码、测试、配置、部署和文档的实际路径。已有 `src/`、`tests/`、`docs/ARCHITECTURE.md`、`Makefile`、`Dockerfile` 时直接引用。多服务仓库写清每个受影响服务和共享组件的检查入口；小型脚本仓库可保留自己的轻量布局。
- **分支、提交与评审**。目标仓库的默认分支、保护规则和审查人登记到项目卡。使用项目已有分支和提交规范；缺少约定时，任务分支加 Issue 编号，提交用 `feat:`、`fix:`、`docs:` 等前缀。接入后在真实 PR 中核对检查名称，再由维护者按需要将其设为合并条件。
- **配置与代码风格**。格式化和静态检查调用项目现有工具，前端可沿用已有 ESLint 或 Prettier 配置。配置名与示例值可放入 `.env.example`，真实值由所用环境注入；审查日志、测试样本与构建产物中是否意外包含凭据。容器交付的项目同时标明镜像摘要；库和 CLI 项目标明包版本及安装验证。
- **谁更新哪份资料**。通用操作写进技能，项目事实写进项目卡，单个需求与发布记录各建副本。PR 完成的定义包含受影响的文档、测试和证据。发布完成后用变更日志记下用户可见的变化和下一步兼容要求。

## 3 · 把第一版送到用户手中

| 节点 | 负责人要回答的问题 | 记录位置 |
| --- | --- | --- |
| 需求与评审 | 这次改变哪一个用户行为？什么输入应通过，什么输入应失败？由谁确认？ | Issue → 规格或 PR 验收项 → 代码审查与测试。 |
| 发布候选 | 评审、CI 和预演的是哪个提交或不可变产物？依赖、环境和配置是否一致？ | 在发布单登记提交 SHA、产物 ID、CI 链接、预演结果。重新构建产生新制品时，重做相应验证。 |
| 放行或暂缓 | 每项证据由谁核对？出现何种现象应停止扩大发布？怎样恢复？ | `docs/harness/RELEASE.md` 的版本副本保存详细证据；工作簿的“发布门禁”保存结论和证据入口。 |
| 发布与观察 | 当前用户实际使用哪个版本？核心操作和指标是否在事先约定的范围？ | 填实际时间、环境、执行人、部署记录、观察结果。若回滚，另记恢复目标、恢复验证与跟进 Issue。 |
| 复盘 | 影响用户的问题是实现缺陷、验收遗漏还是操作问题？第二个项目能复用哪一项改进？ | 项目变更记入业务变更日志；可复用规则作为文件包本身的想法，进入下一轮评估。 |

Excel 的基础发布检查有七项：G01 需求与评审、G02 测试与构建、G03 交付物与预演、G04 回滚准备、G05 监控与发布责任、G06 数据迁移、G07 外部依赖或权限变更。G06 和 G07 可按变更范围填写“不适用”，同时记录判断人和理由。例：纯文案变更，差异仅涉及 Markdown，无数据结构或数据写入。发生不可逆数据变更时，需要验证可行的恢复或前向修复方案，单独确认应用回退后的数据兼容性。

纯静态站点可按 `adapters/github-pages/README.md` 接入手动发布工作流，使用经检查的同一次构建制品。服务端、数据库和任务型项目在项目卡中指向各自真实的平台操作、健康检查、恢复步骤和责任人。托管平台、运行权限和入口在目标项目确定后填写。

## 4 · 用 Excel 管项目与版本

独立下载的工作簿与包内 `workbook/AI-Native-Harness.xlsx` 内容相同。选择一份作为团队在用副本。首次使用，将“实施清单”“发布门禁”“版本记录”起始行中的 `PROJECT` 和 `v0.1.0` 换为真实项目与版本，再在“版本驾驶舱”的 B5、F5 输入同一组值。四张台账各预留 100 行，第 7–106 行带计算或校验；用完可将历史工作簿归档，以干净副本承接新一批。接手人先读“使用说明”即可了解各项填写口径。

| 工作表 | 何时更新 | 能决定什么 |
| --- | --- | --- |
| 版本驾驶舱 | 选择项目和目标版本后查看 | 哪些实施项仍未完成，发布准备是否齐全。实际生产结果查“版本记录”。 |
| 实施清单 | 接入模板、执行变更或处理阻塞时 | 谁处理哪项行动，完成标准和证据在哪里。 |
| 发布门禁 | 候选提交、环境或证据变更时 | 谁核对过每个条件，哪些条件阻止进入发布评审。 |
| 想法池 | 收到新建议或做取舍时 | 谁补证据，何时复查，哪一版承接，怎样判断已经交付。 |
| 版本记录 | 排期、预发布、上线或回滚时 | 某项目某版本的真实结果、证据链接及后续动作。 |
| 使用说明 | 首次接入、切换项目或增加记录前 | 状态含义、填写口径和预留行的扩展方式。 |

仓库中的 Issue、PR、CI 和发布单保存原始记录；Excel 用于跨项目跟踪和定位证据。两边靠项目代号、业务版本、想法编号及链接手工关联。可用同一个教学案例练习：阅读 `examples/iteration-walkthrough.md`，再按 `example/README.md` 在临时目录试跑四项业务测试、一次故意失败和一次恢复。

## 5 · 后来增加的想法怎样进入版本

1. 新想法先写“一类用户在什么场景遇到什么问题”，附例子，分配项目内唯一的想法编号，如 IDEA-001。先查相似记录，追加新证据。
2. 由负责人比较对用户结果的影响、实现代价、依赖、风险与本期容量。采纳的部分绑定目标版本、实施 Issue 和一条可验收标准；暂缓写明复查触发条件或日期；拒绝保留理由。
3. 变更已排期事项时，说明对当前验收条件、发布日期和已有用户的影响。必要时拆成“本次验证”和“以后扩大范围”两条。上线后用实际结果回写，回滚时保留原始发布和恢复记录。
4. 单个项目的差异先留在自己的项目卡、配置或局部规则中。若另一个项目也能复现相同问题，或有可重复的独立样例，可以提议纳入公共模板，在另一个项目副本验证后再发新版。

**把一条新建议交给 Codex**

> 新建议是「……」，来源是「……」，关联项目或既有 Issue 是「……」。先找相似条目，比较影响、投入和验证方式。写出可独立验收的最小改动、应留在项目或应纳入通用模板的理由、建议目标版本，以及暂缓部分的复查条件。把评估补入对应记录；已获采纳的范围再进入实现。

## 6 · 第一次使用时打开哪些文件

| 目标 | 从这里开始 |
| --- | --- |
| 维护者接入真实仓库 | `repo/AGENTS.md`、`repo/docs/harness/PROJECT.md`、`repo/harness.config.json` |
| 负责人跟踪一次版本 | 工作簿的“版本驾驶舱”及 `repo/docs/harness/RELEASE.md` |
| 先看一个完整例子 | `examples/iteration-walkthrough.md`，含一次灰度失败、回滚和下版验收 |
| 接管模板，发布自己的下一版 | `MAINTENANCE.md`、`VERSION`、`CHANGELOG.md`、`KIT-FILES.txt`、`tools/kit.py` |

设计来源为用户提供的《结合你提供的〈Claude Code 实战：Harness 工程之道〉》文本。本指南沿用其中四层架构、四阶段引入和规范驱动开发思路，补充了跨项目接入、真实 CI、版本证据、恢复与升级流程。客户端与平台配置的官方资料见 `repo/docs/harness/EXTENSIONS.md` 和 `adapters/github-pages/README.md`。
