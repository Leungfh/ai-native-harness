# 想法收集与版本决策

每条想法从一个 GitHub Issue 开始，优先使用仓库的「迭代想法」表单。Issue 保留讨论、证据和最终决定；如果反馈先进入 Excel，则建立或找到相应 Issue，再补上链接。工作簿「想法池」类工作表按项目代号与想法 ID 对应该条记录。

## 收到一个想法

1. 搜索相似问题。重复反馈追加到原 Issue，注明来源和差异。涉及多个项目时，分别创建有明确责任人的跟进 Issue，并互相引用。
2. 为新条目分配当前项目内未使用的 `IDEA-001` 形式的编号，记录项目、问题和受影响场景、证据、期望结果，以及负责人。无法重现时，写明需要谁补充哪些输入。
3. 评估影响范围、结果能否验证、投入、依赖及风险。可将想法拆成一项最小实验和后续扩大范围的单独任务。以项目当前版本目标判断是否排期，保留取舍理由。

| 决策 | 何时选择 | 需要补齐的记录 |
| --- | --- | --- |
| 待评估 | 新提交或证据不足 | 待确认问题、下一动作、负责人 |
| 采纳 | 本轮或后续具体版本愿意投入 | 目标业务版本、负责人、可验收结果、实施 Issue 或规格链接 |
| 暂缓 | 方向可行，尚有依赖或窗口未到 | 原因、复查日期或触发条件、复查人 |
| 拒绝 | 超出产品目标或代价高于收益 | 决定人、理由、可重开的新证据 |
| 已交付 | 对应变更实际发布并完成约定观察 | 实际版本、PR、发布或回滚记录、复盘结论 |

## 决策记录

把以下内容贴到对应 Issue，并在决策变动时追加一条。工作簿记录最新状态和链接。被暂缓或拒绝的条目可在新证据出现后回到待评估。

| 字段 | 本次填写 |
| --- | --- |
| 项目代号 / 想法 ID / 日期 / 决定人 | |
| 证据与可验证的目标 | |
| 决策 / 理由 / 本次采纳的范围 | |
| 负责人 / 目标版本或复查时间 | |
| 实施 Issue / 规格 / PR | |
| 发布单 / 实际版本 / 观察与后续动作 | |

已采纳条目的新要求如果改变现有验收标准或版本承诺，先在原 Issue 写清影响，再由负责人决定调整本版范围或另建后续 Issue。同一条想法因回滚而未达到目标时，保留发布事实，重新评估未完成的结果。
